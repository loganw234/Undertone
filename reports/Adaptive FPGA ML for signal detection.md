# Mutable FPGA weights await a closed learning loop

As of November 2026, every ingredient of an FPGA model whose weights stay adaptable at fabric speed has been demonstrated separately, but no published system assembles them on a live signal stream, and none does so on an Alveo U50. Runtime-reloadable weights exist in maintained dataflow tooling (FINN's `internal_decoupled` mode) and in SLAC's SNL library, which is installed at the DIII-D tokamak; in-fabric per-sample learning has reached 50 to 140 ns per update for tiny Kolmogorov-Arnold networks in post-route results; and a host-trains, FPGA-swaps reinforcement-learning loop runs at 2.8 µs at a storage ring. Yet no paper reports a measured weight-swap latency, none uses on-card HBM as a replay store, and nobody has shown a fast detector updated online from labels of the events it missed, with sensitivity compared before and after at a fixed false-alarm rate. OpenTPU itself is a 2017 PyRTL artifact its authors never synthesized: its weights-as-data, double-buffered design is the right idea, but it is a reading reference rather than a code base, nearly all of its open overlay peers are abandoned, and the living toolflows (hls4ml, FINN, LUT networks) earn their nanosecond latency precisely by baking weights into logic. The U50 has ample fabric for a small mutable model (about 704K LUTs and 4,920 DSP slices remain after the standard shell), but AMD discontinued it in April 2026, its last Vitis platform dates from April 2022, its runtime is Linux-only, and its sole real-time input is one QSFP28 port. On the ML side, learned detectors reach 91 to 95% of matched-filter sensitive distance in Gaussian noise and win only where the classical detector is knowingly sub-optimal, small CNNs have collapsed to zero sensitivity on real glitchy noise, and unsupervised self-adapting models have mostly ended up worse than a frozen copy on long benchmarks. The implication for a project "beyond OpenTPU" is that the available novelty lies less in a new accelerator than in closing that loop on one card and measuring it honestly.

The card in hand has no network port, so the QSFP28 and Ethernet ingest paths described below are unavailable: all data moves over PCIe, and HBM replay or on-card signal generation is the signal source, not a first stage before a live digitizer.

## OpenTPU's weights-as-data design is sound, but its code and overlay peers are dead

OpenTPU is UC Santa Barbara ArchLab's PyRTL re-implementation of Google's first TPU, written without a published spec and not binary compatible with the real chip ([OpenTPU README](https://github.com/UCSBarchlab/OpenTPU)). It models an instruction-driven overlay: a square, parametrizable array of 8-bit multiply-accumulate units (shipped examples use 8x8 and 16x16, with 256x256 as the design goal), 32-bit accumulators, ReLU or sigmoid activation, and seven opcodes. The `RW` instruction loads one weight tile from weight DRAM into a four-entry FIFO, and **each MAC carries two 8-bit weight buffers so the next tile can be programmed while the current one computes**, with `MMC.S` flipping the active buffer as the first vector propagates ([OpenTPU README](https://github.com/UCSBarchlab/OpenTPU)). Weights are therefore data, never synthesized constants, which is exactly the property this project wants. Everything around that property is absent. The README states that memory controllers "are currently emulated with no simulated delay", that convolution, pooling and programmable normalization are missing, that scope is the inference phase only, and that "we do not have hard synthesis figures for the full 256x256 OpenTPU". The repository has seen **no push since 2017-12-06** ([GitHub API](https://api.github.com/repos/UCSBarchlab/OpenTPU)); issues from 2019 to 2025 remain open with no maintainer activity ([issues](https://github.com/UCSBarchlab/OpenTPU/issues)), including a 2025 report of an error around the signed-multiply helper ([issue #8](https://github.com/UCSBarchlab/OpenTPU/issues/8)), and a community pull request for Verilog export has been open and unmerged since January 2026 ([PR #11](https://github.com/UCSBarchlab/OpenTPU/pull/11)). PyRTL itself is alive, with version 1.0.3 uploaded in August 2026 ([PyPI](https://pypi.org/project/pyrtl/)).

The only documented run on real hardware is a June 2026 Harvard Library Innovation Lab note describing a hand port to SystemVerilog on an Artix-7 board. Its output matched a NumPy reference on a 200-vector benchmark, but it reports only relative speed (about 2x end-to-end and 4x compute-only versus the Python simulator, slower than CPU BLAS on small inputs, with the USB round trip dominating) and gives no clock rate, utilization or absolute latency ([LIL blog](https://lil.law.harvard.edu/blog/2026/06/16/an-open-hardware-tpu-on-your-desk/)). The most active fork last pushed in June 2025 and still lists a compiler, non-8-bit widths and removal of hand-inserted NOPs as future work ([csirlin/OpenTGPTPU](https://github.com/csirlin/OpenTGPTPU)). One name collision deserves care: `FeSens/openTPU`, created in September 2026, is an unrelated SystemVerilog LLM-inference accelerator whose README does not mention UCSB, though its design of weights held in card DRAM so that one bitstream serves all models is the same overlay pattern ([FeSens/openTPU](https://github.com/FeSens/openTPU)). The notes found no fork that adds training or backpropagation, no published Fmax or resource counts for OpenTPU on any FPGA, and no peer-reviewed OpenTPU paper.

**Inference.** OpenTPU's weights are runtime-swappable by construction, but the ISA has no instruction that writes weight memory from the host or from an on-chip learner, and the weight DRAM is a simulation stub initialised from a file. Adding a write path is an addition outside the existing core, not a redesign. From the README's cycle formulas (`MMC` takes L+2N cycles for L vectors on an NxN array; a tile reload takes N²/64 cycles) and an assumed 100 MHz clock, a single-vector dense layer costs roughly 0.35 µs at N=16 and about 5 µs at N=256, and reloading a 256x256 tile costs about 10 µs. An OpenTPU-style overlay is thus inherently a sub-microsecond to tens-of-microseconds design per layer, not a nanosecond one. With zero commits in nine years and a known bug report against the multiplier, OpenTPU should be read as an architectural reference of about 128 commits, not adopted as a dependency.

### Living toolflows bake weights in; overlays that keep them in memory are abandoned

The standard taxonomy explains the split. Streaming (dataflow) architectures build "one distinct hardware block for each layer", while single computation engines execute layers sequentially on one systolic array or matrix-multiply unit and "favour flexibility over customisation"; the overlay's benefit is that "the same bitstream can target many CNNs", its cost "control mechanisms that resemble those of a processor" ([Venieris et al.](https://arxiv.org/abs/1803.05900)). The table below records where each open toolflow stood on 21 November 2026.

Three documented routes make a dataflow design reweightable without a new bitstream. FINN's default `internal_decoupled` memory mode holds weights in LUTRAM, BRAM or URAM, streams them to the matrix-vector unit through a FIFO and "enables runtime weight updates through an AXI-Lite interface"; URAM storage on non-Versal parts such as the U50's requires `runtime_writeable_weights=1` ([FINN memory modes](https://finn-dev.readthedocs.io/en/latest/reference/mem-modes.html)). The source carries a telling caveat: after any AXI-Lite read or write, "always 'flush' the accelerator by first passing a dummy input vector", because stale weights linger in the FIFOs ([FINN source](https://github.com/Xilinx/finn/blob/main/src/finn/custom_op/fpgadataflow/matrixvectoractivation.py)). FINN's third mode, `external`, is documented as experimental, and a March 2026 question asking whether anyone had it working drew no reply ([FINN discussion #1099](https://github.com/Xilinx/finn/discussions/1099)). hls4ml's `BramFactor` exposes large layers' weight arrays as BRAM interface ports so that "a user can use this interface to implement a weight-reloading scheme", yet the docs flag the feature for re-implementation ([hls4ml docs](https://fastmachinelearning.org/hls4ml/advanced/bramfactor.html)), and an extension adding on-chip backpropagation (ENABOL) is known only from workshop slides (snippet-only) ([FastML 2025 slides](https://indico.cern.ch/event/1496673/contributions/6637920/attachments/3127033/5547241/2025%20-%20FastML%20-%20ENABOL.pdf)). SNL was built for the purpose: its "key feature is the ability to dynamically update model weights without requiring FPGA resynthesis", with weights loaded through AXI-Lite registers while AXI-Stream carries inference data, although its benchmark results are synthesis-only and its reload time is not reported ([Rahali et al.](https://arxiv.org/abs/2508.21739)). Vitis AI is a dead end for this card: the Vitis AI Library notes direct U50 owners back to version 1.4.x, and AMD's current line replaces the DPU with an NPU for Versal AI Edge parts ([UG1354](https://docs.amd.com/r/2.5-English/ug1354-xilinx-ai-sdk/Vitis-AI-Library-v2.5-Release-Notes), [Vitis AI 5.1](https://vitisai.docs.amd.com/en/5.1/index.html)).

### Mutable weights cost constant folding, not the pipeline

Dataflow designs get their speed by specialising logic to known weights. The hls4ml jet tagger on an XCVU9P reaches **12.1 ns in 2,891 LUTs with zero DSPs** using distributed arithmetic, and heterogeneous per-weight quantization cuts LUTs by 50 to 95% and DSPs by 50 to 100% on unrolled models ([hls4ml overview](https://arxiv.org/abs/2512.01463)). LUT networks go further, absorbing weights and activations into truth tables for 1 to 21 ns latency, at the price that a tree-based variant must be retrained from scratch when updated ([LUT-network survey](https://arxiv.org/html/2506.07367v1)). The measured price of mutability is modest where it has been measured at all: FINN describes a "slightly higher resource footprint" for the weight streamer and FIFO ([FINN memory modes](https://finn-dev.readthedocs.io/en/latest/reference/mem-modes.html)), and SNL "consistently uses more BRAM and mostly higher FF counts" than hls4ml while posting lower latency on three of four benchmark models, in a comparison that does not isolate how much is due to reloadability ([SNL paper](https://arxiv.org/html/2508.21739v1)). Off-chip weights are riskier: on the U50 itself a weight-streaming dataflow ResNet50 ran in 3.4 ms against 6.0 ms layer-sequential, but on a ZCU102 with less bandwidth the same idea took 578.7 ms against 21.1 ms ([AutoWS](https://arxiv.org/abs/2311.04764)).

**Inference.** A dataflow design that makes weights mutable gives up constant-coefficient multipliers and adder graphs (generic DSP or LUT multipliers return), unstructured pruning and per-weight bit widths (a zero weight no longer deletes logic), and LUT absorption. It keeps full pipelining, an initiation interval of one, no instruction decode and deterministic latency. Stitching the cited numbers across different papers, devices and models gives a rough ladder for small networks: LUT networks at 1 to 20 ns; unrolled constant-weight MLPs at 10 to 30 ns; unrolled designs with register or LUTRAM weights at 50 to 150 ns including a training step; folded or streamed dataflow at 0.3 µs to hundreds of µs; a small systolic overlay at 0.3 to tens of µs per layer; DPU-class overlays at 3 to 15 ms. No single source benchmarks one small model both ways on one FPGA, so this ladder is indicative only. Where weights sit sets both update cost and latency: registers and LUTRAM give fully parallel reads but cost more per bit; BRAM and URAM are dense but have one or two ports, forcing folding and microsecond latency; DRAM or HBM forces streaming.

## The U50 is roomy, discontinued, Linux-bound and fed through one QSFP28

### Fabric is plentiful, and the 8 GB of HBM is a buffer rather than a weight store

The card carries a two-SLR XCU50 with **872K LUTs, 1,743K registers, 5,952 DSP slices, 47.3 Mb of block RAM, 180.0 Mb of UltraRAM and 24.6 Mb of distributed RAM**, 8 GB of in-package HBM2 and no DDR4 ([DS965](https://docs.amd.com/r/en-US/ds965-u50/Product-Details)). Under the standard Gen3x16 XDMA shell, the user region offers 351K + 353K LUTs, 552 + 564 block RAM tiles, 272 + 272 UltraRAMs and 2,352 + 2,568 DSPs across SLR0 and SLR1 at a default 300 MHz kernel clock, and all 32 HBM pseudo channels attach to SLR0 only ([UG1120](https://docs.amd.com/r/en-US/ug1120-alveo-platforms/U50-Gen3x16-XDMA-base_5-Platform)). Other sources quote somewhat different user budgets: a synthesis-only hls4ml design on this platform reports denominators of 744,638 LUTs and 5,948 DSPs ([arXiv:2609.23141](https://arxiv.org/html/2609.23141)), and a Vitis Libraries page lists a DSP budget of 5,936 (search summary) ([Vitis Libraries](https://docs.amd.com/r/2024.2-English/Vitis_Libraries/hpc/user_guide/L2/benchmark/cg_gemv_jacobi.html_2)), so the 4,920-DSP figure derived from UG1120 should be confirmed against a real build. The HBM is two 4 GB stacks split into 32 channels of 256 MB ([UG1371](https://docs.amd.com/r/en-US/ug1371-u50-reconfig-accel/Card-Features)), and its rail is capped at 10 W: AMD gives **201 GB/s nominal** and 316 GB/s peak under a non-PCIe-compliant condition ([DS965](https://docs.amd.com/r/en-US/ds965-u50/Product-Details)), which contradicts third-party listings quoting 460 GB/s (search summary) ([Avnet](https://my.avnet.com/ebv/products/new-products/npi/2019/xilinx-xilinx-u50)).

No HBM latency measurement exists for the U50 itself. On the sibling U280, an idle HBM read takes 48 to 62 cycles at 450 MHz (106.7 to 137.8 ns), rising to 122 to 171 ns through the hardened switch, with 13.27 GB/s per channel and longer stalls when a read coincides with the periodic refresh ([Shuhai](https://arxiv.org/abs/2005.04324)). MicroRec, the best published HBM-plus-MLP design, kept small tables in BRAM and URAM because on-chip access takes about a third of the HBM or DDR time, and its end-to-end inference for embedding lookups plus a 1024-512-256 MLP took 16.3 to 31.0 µs on a U280 ([MicroRec](https://arxiv.org/abs/2010.05894)). The notes found no published design that stores network weights in HBM for a low-latency model or uses HBM as an online-learning replay buffer; published uses are embedding tables and streaming sample buffers.

**Inference.** One HBM fetch consumes 10 to 17% of a 1 µs budget and adds refresh jitter, so hot weights belong in registers, LUTRAM, BRAM or URAM next to the multipliers. Summing memory blocks under the XDMA shell gives a ceiling near 25 million 8-bit or 12.6 million 16-bit weights on chip, of which 50 to 70% is a realistic planning share, and one multiply-accumulate per DSP per clock bounds a 300 MHz design at roughly 1.5 million MACs inside a 1 µs window. A fully parallel mutable network is therefore limited to a few thousand weights evaluated per pipeline stage, which supports thousands to low tens of thousands of weights at tens of nanoseconds, or up to about a million at a few microseconds with time-multiplexing. For the small model this project targets, multipliers and memory-port bandwidth bind, not storage, and the HBM's natural jobs are a multi-second pre-trigger ring buffer of raw samples, deterministic replay of recorded datasets (8 GB holds about 2.1 billion complex 16-bit samples, some 4.3 s at 500 MS/s), an experience or replay store for training, and a staging area for the next weight set.

### AMD ended the product in 2026 and froze its tooling in 2022

AMD's discontinuation notice XCN26004 of 27 April 2026 lists the A-U50-P00G-PQ-G and its variants with "No Direct Replacement": **last-time-buy orders closed on 30 October 2026**, final shipments end on 2 April 2027, and returns for quality issues are accepted until 2 April 2030 ([XCN26004](https://docs.amd.com/v/u/en-US/XCN26004)). The notes record a conflict that the fetched notice resolves: a distributor employee wrote in June 2026 that there was no indication of end-of-life ([DigiKey forum](https://forum.digikey.com/t/amd-u50-eol/69606)), six weeks after the notice was issued. The newest documented development platform is still `xilinx_u50_gen3x16_xdma_5_202210_1`, released in April 2022 with 2022.1 tools ([UG1120](https://docs.amd.com/r/en-US/ug1120-alveo-platforms/U50-Gen3x16-XDMA-base_5-Platform)); XRT 2024.1 removed the U50LV, U55N and U280 platforms but not the standard U50 one ([UG1451 2024.1](https://docs.amd.com/r/2024.1-English/ug1451-xrt-release-notes/New-Features-and-Changes)). Whether v++ in 2025.x or 2026.x still accepts that platform is unverified.

Licensing changed underfoot. Through Vivado 2025.2, Alveo parts sat in the licence-free Standard edition (search summary) ([UG973 2025.2](https://docs.amd.com/r/en-US/ug973-vivado-release-notes-install-license/Supported-Devices)). From 2026.1, "if no valid license file is found, AMD Vivado does not launch", and the 2026.2 device table lists Alveo as "Supported through the dedicated Alveo tier only" ([UG973 tiers](https://docs.amd.com/r/en-US/ug973-vivado-release-notes-install-license/Device-Availability-by-Subscription-Tier)). AMD's licensing page offers card buyers a free one-year Alveo-tier subscription (search summary; the page was not opened) ([Vivado licensing](https://www.amd.com/en/products/software/adaptive-socs-and-fpgas/vivado/vivado-licensing-options.html)); whether an owner who bought the card before 2026 qualifies, and what happens when the year lapses, is undocumented in anything the researchers could open. The hardened 100G MAC needs only a no-charge licence ([OpenNIC shell](https://github.com/Xilinx/open-nic-shell)). Among open-source shells, OpenNIC lists the U50 but says it "has worked in a lab setting but with minimal testing" and targets Vivado 2020.x to 2022.1 ([OpenNIC shell](https://github.com/Xilinx/open-nic-shell)), Corundum lists the U50 with PTP timestamping and an application section for custom logic ([Corundum](https://github.com/corundum/corundum)), and Coyote, which has ready-made HBM plumbing, does not list the U50 at all ([Coyote](https://github.com/fpgasystems/Coyote)).

**Inference.** A spare or second U50 now comes only from distributor stock or the secondary market. Pinning the toolchain to a 2022.x to 2025.2 release avoids the licence question and matches what the frozen platform and every open U50 shell were written against. Any design should be kept portable to the U55C, the card that Coyote and hls4ml's Coyote backend target ([hls4ml Coyote backend](https://fastmachinelearning.org/hls4ml/autodoc/hls4ml.backends.coyote.html)).

### A Windows 11 workstation can build bitstreams but cannot run the card's runtime

XRT's system requirements name Linux as the host for PCIe accelerator cards and reserve Windows for AMD NPUs ([XRT requirements](https://xilinx.github.io/XRT/master/html/system_requirements.html)); that page dates from 2022, and the notes found no newer AMD statement on Windows support for U-series cards. WSL2 offers no PCI passthrough for such devices (search summary) ([WSL issue 5492](https://github.com/microsoft/WSL/issues/5492)), and OpenNIC, Corundum and Coyote all ship Linux kernel drivers. Outside XRT, AMD publishes reference XDMA and QDMA drivers for Windows, described as lab-test starting points that may need test-signing mode (search summary) ([PG195](https://docs.amd.com/r/4.1-English/pg195-pcie-dma/Device-Drivers)). The card is also passively cooled at up to 75 W ([DS965](https://docs.amd.com/r/en-US/ds965-u50/Product-Details)), and AMD's debug guide warns that "workstations do not provide enough airflow to cool passive cards" (search summary) ([Alveo debug guide](https://xilinx.github.io/Alveo-Cards/master/debugging/build/html/docs/card-install)). JTAG access needs a separately sold programming cable ([DS965](https://docs.amd.com/r/en-US/ds965-u50/Product-Details)).

**Inference.** The Vitis/XRT flow needs a bare-metal Linux boot on the machine that physically hosts the card, by dual boot or a second box. A pure Vivado RTL flow can be built on Windows and loaded over JTAG, and a custom design could talk to AMD's Windows reference drivers, but that is an unsupported lab path. A ducted fan or shroud across the heatsink is a prerequisite in a tower case, not an option.

### Real-time samples arrive only as Ethernet packets

The U50 has one QSFP28 cage (100 GbE, 40 GbE or 4x10/25 GbE), a PCIe edge and a maintenance connector, with no general-purpose I/O for an ADC ([UG1371](https://docs.amd.com/r/en-US/ug1371-u50-reconfig-accel/Card-Features)). Real-time ingest therefore means an external digitizer that packetizes samples. Open transmit-side designs exist: the CASPER RFSoC 4x2 tutorial sends 2,048 time samples per 8,256-byte payload over 100 GbE with jumbo frames and RS-FEC on by default ([CASPER tutorial](https://casper-toolflow.readthedocs.io/projects/tutorials/en/latest/tutorials/rfsoc/tut_100g.html)), and Strathclyde's `rfsoc_qsfp_offload` packetizes RF-ADC data into UDP through the CMAC core ([rfsoc_qsfp_offload](https://www.github.com/strath-sdr/rfsoc_qsfp_offload)). A USRP X410 delivers up to 500 Msps but needs a single 100 GbE link for every two full-rate channels, and an X440 at 1.6 GHz needs one link per channel ([UHD manual](https://uhd.readthedocs.io/en/latest/page_usrp_x4xx.html)). On the receive side, the Vitis Network Example provides a 100 Gbit/s UDP stack for Alveo kernels ([VNx](https://www.github.com/Xilinx/xup_vitis_network_example)). PCIe from the host is the alternative, but AMD itself calls PCIe transfers expensive without giving a figure (search summary) ([UG1700](https://docs.amd.com/r/en-US/ug1700-vitis-accelerated-data-center/Working-with-Alveo-Accelerator-Cards)), and a tuned DPDK loop with an X410 measured worst-case round trips just under 65 µs (search summary) ([Laskos et al.](https://www.tkn.tu-berlin.de/bib/laskos2025latency/laskos2025latency.pdf)). Sibling cards are used at scale as 100 GbE-fed signal processors, including 20 U280s in ASKAP's CRACO and 400 U55Cs in SKA-Low ([Pritchard et al.](https://arxiv.org/html/2601.07130)), but the notes found no published U50 real-time signal design, no receive latency for the UltraScale+ CMAC with or without RS-FEC, and no measured XDMA or QDMA small-transfer latency on any Alveo card.

**Inference.** Four ingest modes follow, in descending realism for "real time": digitizer to 100 GbE to CMAC to model, the only path that keeps an operating system out of the data plane; the same at 4x10/25 GbE for cheaper radios; PCIe from the host, suited to replay, weight updates and readback; and replay from HBM, which gives full-rate, deterministic timing with no external hardware. On the Ethernet path, packetization dominates latency: filling a 2,048-sample packet takes about 4.1 µs at 500 MS/s, so a sub-microsecond target needs much smaller packets or processing that starts on the first word. An RFSoC running CASPER- or Strathclyde-style firmware is the more open transmitter, because the U50 must parse the radio's wire format in RTL and the CASPER format is a sequence counter plus raw samples.

## In-fabric learning spans 50 ns to seconds, and nobody has measured the swap

### Tiny models learn per sample in nanoseconds to microseconds

Full backpropagation on one FPGA is well demonstrated for CIFAR-10-class CNNs, but it is the wrong regime here: such trainers use 93K to 189K LUTs, and one group estimates that "it takes over one year to implement an error-free training accelerator on FPGA" against a week for inference ([LocalTrain](https://arxiv.org/html/2610.17099v1), [BOOST](https://phwl.github.io/assets/papers/boost_iccad23.pdf), [Zhao et al.](https://arxiv.org/html/2411.05873v1)). The relevant results are the small ones. The headline is a 2026 MIT design that runs forward pass, backward pass and in-place update of a Kolmogorov-Arnold network in one kernel: **50, 70 and 140 ns per complete online update** on an XCVU13P, using between 430 LUTs with 4 DSPs and 10,592 LUTs with 84 DSPs, with no BRAM ([Hoang et al.](https://arxiv.org/html/2602.02056v4)). Its caveats matter. The results are post-route, not measured on a board; the models have 13 to 273 parameters; learning is batch-size-one SGD with compile-time learning rates; no repository is linked; and the paper's "sub-100 ns" claim conflicts with its own 140 ns qubit-readout figure. Its central argument is numerical: because B-spline values lie in [0,1], activations and gradients stay bounded, and in a drifting qubit-readout benchmark the fixed-point KAN held 92.8% where quantized MLPs sat near 50% and a floating-point OS-ELM scored 41.8%.

Older small-MLP work frames the cost of backpropagation in fabric. A 2018 Kintex-7 design found the backpropagation training core "takes up 3x more LUTs and 10x more FFs" than a weight-perturbation core on a small network, and at low precision weight perturbation reached 94.7% on Iris where backpropagation reached 52%; on a 32-16-8-16-32 RF anomaly autoencoder the update rates were once every 1.3 µs and 2.5 µs respectively (PDF text extraction; units inferred) ([Siddhartha et al.](https://phwl.github.io/assets/papers/wp_fpt18.pdf)). That paper also introduced the pattern this project most needs: ping-pong parameter buffers "such that the training core and the prediction core can operate side-by-side", with a multiplexer toggled when a new parameter set is ready. The one training result located on the Alveo U50 itself is a tensor-compressed transformer trainer that fits all parameters and gradients in under 6 MB of BRAM and 22.5 MB of URAM ([Tian et al.](https://arxiv.org/abs/2501.06663)); it sits outside the low-latency regime, and the notes' dedicated survey of on-FPGA training found no other U50 work.

### Lightweight learners trade accuracy for multiplier-free or closed-form updates

Three families stand out beyond gradient descent. OS-ELM, a rank-one recursive-least-squares update of a random-feature autoencoder, is the most mature drift-tracking anomaly detector: ONLAD's forgetting mechanism held AUC at 0.869 to 0.899 under concept drift against 0.575 to 0.591 with forgetting disabled ([ONLAD](https://ar5iv.labs.arxiv.org/html/1907.10147)), though published implementations are sequential HLS at about a millisecond and one later design resorted to 64-bit floating point because error only converged above 20 fractional bits ([OSOS-ELM](https://arxiv.org/html/2504.09028v1)). Tsetlin-automaton learners use only increment, decrement and compare: TsetlinWiSARD keeps LUT contents and automaton states in distributed RAM, which makes a LUT-style network's "weights" writable at run time without partial reconfiguration ([TsetlinWiSARD](https://arxiv.org/pdf/2603.24186)), and an earlier Tsetlin architecture demonstrated adding an unseen class at run time and recovering from 20% stuck-at faults by continued learning ([Prescott et al.](https://ar5iv.labs.arxiv.org/html/2306.01027)). Classical adaptive filters set the speed baseline and a warning: a 64-tap complex LMS filter updates in 58.6 ns on an RFSoC, yet its frozen output "shows no resolved improvement in readout fidelity" over boxcar integration ([Johnson et al.](https://arxiv.org/html/2610.00783v3)). At the other end of maturity, the notes found no FPGA implementation of equilibrium propagation, target propagation, SPSA or forward-gradient training, and Forward-Forward exists only as a bachelor-thesis design (snippet-only) ([TU Delft](https://repository.tudelft.nl/record/uuid:92d6de17-392c-450a-9af4-4156a93fb445)).

**Inference.** The LMS result suggests a linear adaptive front end feeding a threshold adds little discrimination; gains for faint signals should come from nonlinear learners or matched-filter weighting. And every in-fabric learner cited assumes a supervision signal, whether labels, reconstruction error, reward or confident self-prediction. For "events previously missed", the choice of that signal constrains the algorithm more than FPGA resources do.

### Host-trains, FPGA-swaps is the best-proven loop

The strongest end-to-end example is KIT's KINGFISHER controller at the KARA storage ring. A small actor network runs on a Versal with **a whole-loop latency of 2.8 µs**, FPGA logic streams observations and actions to DDR as an experience accumulator, PPO trains on a control-room computer, and new parameters are "loaded onto the AIE kernel at run-time" after each 2,048-step episode; the weight-transfer time is not stated and code is available on request only ([KINGFISHER](https://arxiv.org/html/2409.16177v1)). SNL supplies the same reload capability to fusion diagnostics, with a KCU1500 card installed in DIII-D's plasma control system nodes and a reported inference latency near 4.4 µs (snippet-only) ([arXiv:2604.26042](https://arxiv.org/abs/2604.26042)). When the structure rather than the weights must change, dynamic partial reconfiguration costs 0.11 to 0.17 s on an Alveo U200 ([Kang and Park](https://pmc.ncbi.nlm.nih.gov/articles/PMC12736569/)). Across all of this work one number is missing: no paper reports measured weight hot-swap latency or maximum update rate for AXI-Lite or streamed updates over PCIe or Ethernet on an Alveo-class card.

**Inference.** The KINGFISHER split maps directly onto a U50: fabric model, HBM as experience store, host training over PCIe, weights swapped atomically. FINN's flush caveat shows that streamed-weight designs hold stale weights in FIFOs, so an atomic swap needs either a ping-pong memory with a select bit, which is OpenTPU's two-buffers-per-MAC idea, or an explicit quiesce. Partial reconfiguration is two to five orders of magnitude slower than memory-mapped writes and is justified only when topology changes.

### Fixed-point learning fails silently on exactly the faint updates

The documented failure modes are specific. In the RFSoC LMS design, coefficient updates truncate toward zero at the least significant bit, so sub-LSB updates vanish and a filter below that amplitude floor can train to all-zero coefficients with nothing flagging it ([Johnson et al.](https://arxiv.org/html/2610.00783v3)). Naive integer SGD saturates most values at ±127 or 0 unless results are rescaled by effective bit width, and pseudo-stochastic rounding recovers the accuracy of true stochastic rounding without a random-number generator ([NITI](https://ar5iv.labs.arxiv.org/html/2009.13108)). Softmax is "highly susceptible to both under and overflow in fixed-point arithmetic" ([Siddhartha et al.](https://phwl.github.io/assets/papers/wp_fpt18.pdf)). Short-period LFSR imbalance biased on-chip Tsetlin feedback enough to drop accuracy below software ([TsetlinWiSARD](https://arxiv.org/pdf/2603.24186)). The mitigations in print are weight stores wider than compute operands (INT16 master weights and a 48-bit gradient accumulator around INT8 arithmetic in [LocalTrain](https://arxiv.org/html/2610.17099v1)), saturating arithmetic with convergent rounding, forgetting factors, and gated learning, in which a drift detector, an operator or an on-chip accuracy check decides when to learn ([ODL on Pico](https://arxiv.org/html/2203.01077v4), [Prescott et al.](https://ar5iv.labs.arxiv.org/html/2306.01027)). The one FPGA replay design surveyed keeps a short-term store of only about 0.3 MB on chip with a long-term store off chip (read through PDF text extraction; re-check before quoting) ([Chameleon](https://www.comp.nus.edu.sg/~tulika/DATE_2023.pdf)). The notes found no long-horizon study of fixed-point online learning, no evaluated shadow-model rollback, and no FPGA work using HBM for replay.

**Inference.** The sub-LSB stall is the hazard most relevant to faint signals, because small error-driven updates from weak events are exactly what a truncating update discards. A forgetting factor cuts the other way: an always-on semi-supervised learner will absorb a persistent weak signal into "normal" and stop flagging it, and none of the FPGA works evaluates learning a rare positive without absorbing it.

## Only particle physics runs FPGA ML in production, and every fielded model is static

High-energy physics is the one domain where FPGA ML is routine. CMS runs three hls4ml-built networks in its Run 3 Level-1 trigger ([hls4ml overview](https://arxiv.org/html/2512.01463)): a displaced-muon network at 83 ns deployed in June 2023 ([arXiv:2509.21062](https://arxiv.org/html/2509.21062v3)), and the AXOL1TL and CICADA anomaly detectors, which together selected more than four billion collision events during 2024 ([arXiv:2609.31739](https://arxiv.org/abs/2609.31739)). AXOL1TL operates "within a fixed latency of 50 ns" ([FastML 2025](https://indico.cern.ch/event/1496673/contributions/6637931)); its often-quoted footprint of about 2.1% of LUTs comes from conference slides (snippet-only), and the 16-cycle, roughly 100 ns CICADA figure is from a third-party re-implementation rather than official firmware ([arXiv:2511.01908](https://arxiv.org/html/2511.01908v1)). ATLAS runs an anomaly network quantized to fit 25 ns inference ([GELATO slides](https://indico.cern.ch/event/1496673/contributions/6640029/attachments/3128131/5548711/GELATO_FastML_9_3_2025_Kenny.pdf)). **Every one of these models is static in the fabric**: AXOL1TL has moved through offline-retrained versions, including v4 and v5, with the newest switching toolchain from QKeras and hls4ml to HGQ and da4ml ([FastML Foundation](https://fastmachinelearning.org/applications/anomaly-detection-for-new-physics-at-cms-level-1-trigger/)), and the notes found no public retraining cadence and no production system that changes weights at run time.

First, outside physics triggers the field is prototypes: all RF demonstrations are static offline-trained models, and one radar-warning study judged an FPGA LSTM not viable against CFAR partly because it "requires prior training with knowledge of the noise environment" ([journal record](https://www.ebsco.com/articles/technology/42757fd8-b4f9-5f4d-82a4-eb1ec68df25e/performance-evaluation-of-fpga-based-lstm-neural-networks-for-pulse-signal-detection-on-real-time-radar-warning-receivers)). Second, the hardware is often present where the ML is not: radio telescopes field hundreds of Alveo cards for channelization, correlation and RFI flagging, while Breakthrough Listen's in-path FRB detector is a ResNet on GPUs consuming about 100 Gb/s of beamformed spectrograms ([arXiv:2610.07482](https://arxiv.org/pdf/2610.07482)).

Adaptation is named as an unmet need more often than it is delivered. A 2026 position paper argues that "nearly all existing accelerators assume static models trained offline" and that "model updates must occur at the timescale of the underlying physics" ([Hoang](https://arxiv.org/abs/2602.02005)). HBT-EP's authors report that machine upgrades changed plasma conditions enough to require new training data before control experiments ([arXiv:2312.00128](https://arxiv.org/html/2312.00128v3)), CMS describes its trigger menus as "static, hand-tuned" while conditions evolve ([arXiv:2601.08910](https://arxiv.org/abs/2601.08910)), and radio astronomers note that "adaptive systems capable of detection previously unobserved transients are advantageous" as satellite interference grows ([arXiv:2601.07130](https://arxiv.org/html/2601.07130)). On the U50 specifically, the published record is thin: a 175k-parameter recurrent plasma predictor reached 2.64 µs in implementation while using 65% of DSPs, but the authors state that "no physical Alveo U50 card was available to us for direct hardware testing" ([arXiv:2609.23141](https://arxiv.org/html/2609.23141)), and the only measured U50 result is a Vitis AI DPU deployment at 2.6 to 3.7 ms ([arXiv:2307.05152](https://arxiv.org/html/2307.05152v2)). The benchmark suites that anchor this field, FastML Science Benchmarks (jet classification at 55 ns on a VU9P) and MLPerf Tiny (an hls4ml anomaly-detection autoencoder at 19 µs on a Zynq-7020), contain no drift or adaptation track ([arXiv:2207.07958](https://ar5iv.labs.arxiv.org/html/2207.07958), [arXiv:2206.11791](https://ar5iv.labs.arxiv.org/html/2206.11791)).

**Inference.** Three tiers of adaptability exist: retrain offline and rebuild firmware, which is the norm; reload weights at run time into a fixed architecture, fielded only by SNL at DIII-D; and learn in fabric, which has no fielded example in any signal domain. Domains whose inputs are already digital records or packets (trigger objects, network traffic, telescope back-end streams, replayed strain or IQ traces) are the ones an ADC-less U50 can prototype. An on-hardware, 100 GbE-fed, low-latency ML result on a U50 would itself be new relative to the published record found.

## Learned detectors win only where the classical method is knowingly sub-optimal

### Parity in Gaussian noise, fragile wins on real data

Gravitational-wave searches give the cleanest evidence because one mock data challenge compared methods at a fixed false-alarm rate. In MLGWSC-1, the best ML submissions reached up to 95% of matched-filter sensitive distance in simulated Gaussian noise but only 70% in real O3a noise at one false alarm per month, and **two CNNs that reached 40 to 95% of the matched-filter distance on Gaussian noise scored zero on real noise** because background triggers dominated ([MLGWSC-1](https://ar5iv.labs.arxiv.org/html/2209.11146)). A small 6-conv, 3-dense CNN retains at least 91.5% of matched-filter distance in Gaussian noise ([Schäfer et al.](https://ar5iv.arxiv.org/html/2106.03741)). The systems that later beat the challenge's PyCBC configuration on real noise are large: AresGW is a 54-layer ResNet ([Nousi et al.](https://ar5iv.labs.arxiv.org/html/2211.01520)), and Sage, a ResNet50-based design, found 11.2% more injections than PyCBC ([Sage](https://arxiv.org/abs/2501.13846)). In the same challenge a classical wavelet excess-power pipeline with a gradient-boosted ranker beat every ML entry on real noise, at 1229.1 against 1091.8 Mpc ([MLGWSC-1](https://ar5iv.labs.arxiv.org/html/2209.11146)). Claims of newly found events remain contested: AresGW reported eight new O3 candidates ([Koloniari et al.](https://arxiv.org/abs/2407.07820)), while the independent Aframe search of the same data found none of its own ([arXiv:2512.04516](https://arxiv.org/abs/2512.04516)).

Other domains repeat the shape. In seismology, the benchmark for "hidden" events was set by classical template matching, which grew the Southern California catalogue tenfold to 1.81 million earthquakes ([Ross et al.](https://www.osti.gov/pages/biblio/1511259-searching-hidden-earthquakes-southern-california)); EQTransformer, with about 372k parameters, then located 21,092 events in a region absent from its training where a manual study had 8,521 ([Mousavi et al.](https://pmc.ncbi.nlm.nih.gov/articles/PMC7415159)). A SETI search with a variational autoencoder surfaced eight signals of interest that earlier searches had not flagged, after about 2.9 million snippets were initially flagged, and none was re-detected on re-observation ([Ma et al.](https://ar5iv.labs.arxiv.org/html/2301.12670)). In RF detection, a conv-plus-LSTM network moved the SNR wall from about -5.35 dB to about -8.5 dB against an energy detector but degraded sharply across modulation families ([DetectNet](https://ar5iv.arxiv.org/html/1909.02730)), and a 2025 study with unknown carrier offset found a learned classifier about 3 dB better than FFT thresholding for a tone, barely better than the energy detector for QPSK and no better for OFDM ([arXiv:2512.13542](https://arxiv.org/html/2512.13542v1)). At trigger scale, FPGA autoencoders with AUC of 84 to 96% deliver true-positive rates of only 0.05 to 0.13% at a false-positive rate of 1e-5 for three of four benchmark signals ([Govorkova et al.](https://ar5iv.labs.arxiv.org/html/2108.03986)).

**Inference.** The gap to the matched filter is small where it is truly optimal, and ML's wins come from what it does not model: glitches, incomplete template banks, unknown nuisance parameters and noise uncertainty. A small adaptive model should be tested where the classical baseline is knowingly sub-optimal, since parity is the best possible outcome against an ideal matched filter in white noise. For a small FPGA model, the non-Gaussian background rather than faint-signal efficiency is the likely binding constraint, and a cheap classical front end with a small learned ranker is a credible low-parameter design.

### Labels that do not come from the model are the safe way to adapt

The best-evidenced strategy is continuous injection of synthetic signals into live noise. Aframe generates all training data on the fly from real noise and simulated waveforms and constructs hard negatives by "muting" a signal in one detector or "swapping" mismatched waveforms across detectors ([Marx et al.](https://arxiv.org/html/2403.18661v2)); Sage's ablation shows that reducing signal and noise variety "significantly degraded detection and caused overfitting" ([Sage](https://arxiv.org/html/2501.13846v2)). A controlled study of fifteen SNR curricula found no significant difference in final performance from fixed-range training, with networks trained at low SNR generalising to high SNR but not the reverse ([Schäfer et al.](https://ar5iv.arxiv.org/html/2106.03741)). For forgetting control, an empirical survey finds replay the most versatile method in online continual learning ([Mai et al.](https://arxiv.org/abs/2101.10423)), whereas elastic weight consolidation behaves like plain fine-tuning in single-pass online settings (snippet-only) ([arXiv:2501.04897](https://arxiv.org/abs/2501.04897)). Unsupervised test-time adaptation is the least safe option: on a long, continually changing benchmark, all but one state-of-the-art method eventually collapse below the unadapted model, and periodic reset to pretrained weights matches or beats them ([RDumb](https://arxiv.org/abs/2306.05401)). Self-training on a model's own pseudo-labels overfits to its errors unless true-labelled samples anchor each batch ([Arazo et al.](https://arxiv.org/abs/1908.02983)). One finding tempers the premise of adaptation itself: an Aframe model trained on ten days of O3 data held a stable detected fraction across the following ten months, and its authors say a model "can continue to be used for months without retraining" ([Marx et al.](https://arxiv.org/html/2403.18661v2)).

**Inference.** A delayed-label teacher, meaning a slower and more sensitive pipeline, yields labels biased toward events the teacher can see, so the standard positive-unlabelled assumption that labelled positives are selected completely at random ([Bekker and Davis](https://arxiv.org/abs/1811.04820)) will be wrong and the label propensity should be measured with injections through the teacher. If the model learns from its own above-threshold detections it will reinforce loud morphologies and leave the faint threshold where it was. The low-risk design is supervised updates from injections on live noise, a small replay buffer that includes stored hard negatives, a frozen reference copy of the weights, and periodic or drift-triggered rollback. Because noise drift alone may offer little headroom, the experiment needs a source with real regime changes or a deliberately induced shift, and updating only whitening or input normalisation should be the first baseline that weight adaptation must beat. The notes found no published system that closes this loop on real data.

### False alarms, saturation and leakage are the recurring traps

Several pitfalls bear directly on an FPGA implementation. A final softmax saturates to exactly 1 in floating point, which made efficiency collapse below about a thousand false alarms per month until the ranking statistic was taken from unbounded linear outputs ([Schäfer et al.](https://ar5iv.arxiv.org/html/2106.03741)), and AresGW's statistic is still capped by double precision ([Koloniari et al.](https://arxiv.org/html/2407.07820v1)). Metrics mislead: a volume-weighted sensitive distance rewards bias toward heavy systems, so a model can score higher while finding fewer signals ([Sage](https://arxiv.org/html/2501.13846v2)), and AUC hides the low-false-positive behaviour that matters. Training priors narrow sensitivity silently, as when AresGW recovered 34 of 43 known events inside its training mass range and 10 of 55 outside it ([Koloniari et al.](https://arxiv.org/html/2407.07820v1)). Background itself drifts, which is why one hybrid search re-estimates its background at intervals ([arXiv:2512.04516](https://arxiv.org/abs/2512.04516)).

**Inference.** For an adaptive detector the false-alarm rate is not a fixed property of a threshold. Every weight update changes the null distribution of the ranking statistic, so the threshold must be recalibrated on fresh background after each update, or an "improved sensitivity" is merely a lowered effective threshold. Fixed-point arithmetic sharpens the saturation problem, so the statistic's dynamic range in the far noise tail needs explicit bit-width budgeting on pre-activation logits. Evaluating many model snapshots and reporting the best is a selection effect; the notes found no paper stating a trials-factor correction for adaptively updated detectors, nor any study of how false-alarm rate evolves under online updates on real instrument noise.

### The accepted yardstick is efficiency versus SNR at a fixed false-alarm rate

Evaluation practice converges across fields. The MLGWSC-1 protocol defines false-alarm rate as background triggers above threshold divided by background duration, counts an injection as found if a trigger lies within a time window of it, and reports sensitive distance against false-alarm rate with background multiplied by time-slides ([MLGWSC-1](https://ar5iv.labs.arxiv.org/html/2209.11146)). RF work reports probability of detection against SNR at a fixed false-alarm probability, bracketed by the energy detector and the matched filter ([arXiv:2512.13542](https://arxiv.org/html/2512.13542v1)); trigger work reports true-positive rate at a fixed very low false-positive rate ([Govorkova et al.](https://ar5iv.labs.arxiv.org/html/2108.03986)). For streams with delayed labels, "continuous re-evaluation" scores the predictions made between an instance's arrival and its label's arrival ([Grzenda et al.](https://researchportal.ip-paris.fr/en/publications/delayed-labelling-evaluation-for-data-streams/)). AresGW reports about ±3% variance in sensitive distance across test sets at one per month ([Nousi et al.](https://ar5iv.labs.arxiv.org/html/2211.01520)), a noise floor any claimed adaptation gain must clear.

**Inference.** No published protocol exists for before-and-after evaluation of an online-adapting detector at fixed false-alarm rate, so the notes assemble one from these practices. Split the noise stream by time into adaptation periods and evaluation periods the model never trains on, and replay a fixed, pre-registered injection set to every model version. Recalibrate the threshold on held-out signal-free noise after each update and compare at equal false-alarm rate, never at equal threshold. Report efficiency against injected SNR and the count of found injections, with uncertainty across seeds and periods, and label any false-alarm claim below roughly one per background duration as extrapolation. Compare against a frozen model, a frozen model with only normalisation updated, a periodic full retrain, a periodic reset, and the classical bounds on the same injections. Report performance on both newest and earliest noise to expose forgetting.

| UNSW-NB15 / CICIDS2017 | Network traces replayed as PCAP | No SNR concept | Not assessed | [FSNIC](https://arxiv.org/html/2609.16363) |

**Inference.** Self-generated IQ streams are the best first fit: short frames, exact SNR, analytic matched-filter and energy-detector reference curves, existing microsecond FPGA precedents, and non-stationarity that can be injected on purpose. The MLGWSC-1 generator is the hard second stage because it supplies real glitchy noise and published fixed-false-alarm baselines, along with the documented collapse of small CNNs. Seismic noise with scaled events offers a natural delayed-teacher experiment using the template-matching catalogue against the routine one. ADC2021 matches the nanosecond toolchain but tests anomaly detection, not lowering an SNR threshold.

On model size, demonstrated small detectors span trigger-scale dense autoencoders (a 57-32-16-3 encoder at 80 ns on a VU9P, per [Govorkova et al.](https://ar5iv.labs.arxiv.org/html/2108.03986)), compact seismic detectors near 29k parameters (snippet-only) ([LightEQ](https://doi.org/10.1145/3576842.3582387)), and a few conv-plus-LSTM layers for RF. Sage's ablation found that plain deeper ResNets did much worse than a multiscale front end with attention at similar size ([Sage](https://arxiv.org/html/2501.13846v2)), which favours building domain structure into small models over adding depth. The notes found no published efficiency-versus-SNR curve for any model under about 10k parameters on a time-series detection task.

## Four candidate directions and the gaps they could close

Everything in this section is inference from the cited findings; it lays out what the evidence points to and is not a claim from any single source.

| Direction | Published precedent | What would be new | Main risk |
|---|---|---|---|
| A. Host-trained small model with atomic weight swap and HBM experience buffer | KINGFISHER, SNL, ping-pong buffers, OpenTPU's two weight buffers per MAC | Measured PCIe or Ethernet swap latency; HBM as replay store; fixed-false-alarm before/after on one card | Host round-trip time unmeasured; needs Linux host |
| B. In-fabric adaptive head on a frozen or slowly updated front end | KAN SGD at 50 to 140 ns, OS-ELM with forgetting, Tsetlin-WiSARD | First such learner on an instrument-like stream with gated learning and rollback | KAN evidence is one preprint without code; sub-LSB stall; absorbing weak signals into "normal" |
| C. Trainable systolic overlay, an OpenTPU that learns | OpenTPU, the Harvard port, NITI's 32x32 systolic training kernels on a U280 | No published design combines a TPU-style overlay with on-chip training | Microsecond-class latency; every interface must be built |
| D. FINN+ or hls4ml baseline with runtime-writable weights | FINN `internal_decoupled`, hls4ml `BramFactor` | Measured update time and whether inference must pause | Word-by-word AXI-Lite writes; new weights must fit the tool's integer quantization (unverified design risk) |

Direction A carries the lowest algorithmic risk because the host can train in full precision with replay and validate a candidate before any swap, and its unmeasured piece, swap latency on an Alveo-class card, is itself a publishable number. Direction B delivers the lowest adaptation latency and the most direct answer to "ultrafast training", and the KAN result suggests choosing a model whose update is sparse and local (spline coefficients, table entries, weightless RAM nodes) over dense fixed-point backpropagation. The two combine naturally: a frozen or host-updated feature extractor, a fast in-fabric head, ping-pong weights, gated learning, and the host acting as shadow-model validator. Each element has a published precedent; the combination with HBM replay does not. Direction C is the literal "build on OpenTPU" path and is the weakest fit for a low-latency goal, though it is the cleanest route if changing model shape without a rebuild matters more than nanoseconds; NITI's integer training kernels are the closest published arithmetic ([NITI](https://ar5iv.labs.arxiv.org/html/2009.13108)). Direction D is best treated as a quick reference build, since it is the only maintained, documented, in-tree mechanism and FINN+ advertises an Alveo flow. LUT-network methods are the wrong base for adaptivity as published, because any change means retraining and re-running place and route.

For the experiment itself, the evidence points to a staged data path and a narrow claim. HBM or PCIe replay of recorded and self-generated streams comes first, since it needs no external hardware and gives deterministic timing; a 100 GbE digitizer follows only once the loop works. The controlled variable can be the minimum injected SNR, with efficiency at fixed false-alarm rate as the readout, since the curriculum evidence suggests the lower SNR bound matters more than the schedule. A plausible small architecture is fixed or slowly adapted whitening, a small bank of 1-D kernels initialised as matched filters or multiscale wavelets, and a few thousand to tens of thousands of weights producing an unbounded logit, with online adaptation restricted to normalisation and final layers.

The open gaps the notes identify fall into three groups. On hardware: no measured weight hot-swap latency over PCIe or Ethernet; no HBM latency or throughput measured on a U50; no CMAC receive latency with RS-FEC; no small runtime-updated network on a U50 with resource and latency figures; no like-for-like comparison of overlay and unrolled designs for one small model; and no measurement of FINN's runtime-weight update time. On learning: no long-horizon fixed-point online learning study, no evaluated shadow-model rollback on FPGA, no HBM replay buffer, and no common-benchmark comparison of learner families. On detection science: no closed loop from a slower pipeline's later labels to a fast deployed detector with fixed-false-alarm before/after results, no study of false-alarm evolution under online updates, no trials-factor treatment for adaptive detectors, and no efficiency-versus-SNR curve for a sub-10k-parameter time-series model. Practical unknowns sit beside these: whether an existing U50 owner can obtain an Alveo-tier licence for Vivado 2026.x, whether the XCU50 remains in the 2026 device database, and which Vitis release last accepts the 2022 platform.

The figures most in need of re-verification before they carry weight in a design or paper are the DIII-D SNL latency of about 4.4 µs and the AXOL1TL 2.1% LUT footprint (both snippet-only); the 6.4 µs Tsetlin-WiSARD and 1.3/2.5 µs weight-perturbation update times (PDF text extraction with inferred units); the roughly 8 µs RFSoC modulation classifier and the 65 µs DPDK round trip (search summaries); the Vivado Standard-edition coverage through 2025.2, the Alveo-tier terms, the workstation-airflow warning and the Windows reference-driver status (all search summaries); and the conflicting U50 user-region DSP budgets (4,920 against 5,936 to 5,948). The overlay latency ladder and all capacity arithmetic are stitched from different papers and devices and are inference throughout.

## Conclusion

The research reframes what "beyond OpenTPU" should mean. OpenTPU's lasting contribution to this project is a single mechanism, a second weight buffer beside every multiplier so that a new set can be staged while the old one computes, and that mechanism transplants cleanly into an unrolled datapath that the cited figures place one to two orders of magnitude faster than the overlay it came from. The instruction-driven overlay is worth keeping only if the research question is training inside a general-purpose tensor machine. If the question is whether a model can learn to see what it missed, the accelerator becomes the instrument rather than the result, and the scarce commodity is measurement: three numbers the literature does not contain (swap latency on an Alveo-class card, false-alarm behaviour under online updates, and efficiency versus SNR for a model small enough to run in tens of nanoseconds) are each reachable on a single U50 with replayed data.

Two constraints shape how boldly to claim. Months-long stability of a frozen detector on real gravitational-wave noise means adaptation has to be demonstrated against a noise source that actually changes regime, with a frozen model and a normalisation-only model as the opponents to beat, or the experiment will show a null result for the wrong reason. And the card's discontinuation, frozen platform and Linux-only runtime make portability a design requirement from the first commit: a datapath written as plain RTL or HLS against a thin shell, exercised first by HBM replay, survives a move to a U55C or a successor, while anything bound to the 2022 Vitis platform or to Vitis AI does not.
