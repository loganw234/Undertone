# OpenTPU and the landscape of open FPGA ML accelerator architectures/toolflows (runtime-mutable weights focus)

Research date: 2026-11-21. Repository metadata (last push, stars, archived flag, release tags) was read directly from the public GitHub REST API on that date and is cited to the repository URL. "Last push" means the most recent push to any branch. Where a number comes from a search-result snippet rather than a page I fetched in full, it is marked "(snippet)".

## Key Question 1: What is OpenTPU, and what state is it in?

### Takeaway
UCSB ArchLab's OpenTPU is a small PyRTL research artifact (alpha release, last commit 2017-12-06, never officially synthesized or run on a board by its authors) that models a first-generation-TPU-style instruction-driven overlay: 8-bit systolic matrix-multiply array, 32-bit accumulators, ReLU/sigmoid activation, and weights that live in a (simulated) weight DRAM and are streamed in tile-by-tile through a FIFO. Weights are therefore data, not synthesized constants, which is the property the reader wants, but everything around that (real memory controller, host interface, convolution, training, timing closure) is missing, and the project is effectively unmaintained.

#### Architecture (all from the README)
- Instruction set, 7 opcodes: `RHM` (read N vectors from host memory into the Unified Buffer), `WHM` (write N vectors from Unified Buffer to host memory), `RW` (load one weight tile from weight DRAM into the weight FIFO), `MMC.{O,S}` (matrix multiply; `O` overwrites instead of accumulating, `S` switches to the next preloaded weight tile), `ACT.{R,Q}` (activation; `R` = ReLU, `Q` = sigmoid, no flag = passthrough), `NOP`, `HLT`. `SYNC` is not implemented. — [OpenTPU README](https://github.com/UCSBarchlab/OpenTPU)
- Matrix Multiply unit: a "parametrizable array of 8-bit Multiply-Accumulate Units (MACs)", each an 8-bit multiplier plus an adder of 16 to 32 bits. The array must be square; shipped examples use MATSIZE 8 and 16; the design is intended to scale to 256x256. — [OpenTPU README](https://github.com/UCSBarchlab/OpenTPU)
- Each MAC has **two 8-bit weight buffers**, so a new tile can be programmed while the current one is computing; an `MMC` with the `S` flag flips the active buffer as the first vector propagates through the array. — [OpenTPU README](https://github.com/UCSBarchlab/OpenTPU)
- Weight path: at 256x256 a weight tile is 64 KB; a 4-entry FIFO buffers tiles; the weight-DRAM interface is assumed to be "a standard DDR interface moving data in 64-byte chunks". — [OpenTPU README](https://github.com/UCSBarchlab/OpenTPU)
- Memory controllers "are currently emulated with no simulated delay"; the host-memory connection is "currently the size of one vector". — [OpenTPU README](https://github.com/UCSBarchlab/OpenTPU)
- Accumulators: MM results go to a software-specified accumulator address, with overwrite or accumulate selected by the instruction. `MMC` reads the Unified Buffer and writes accumulators; `ACT` does the reverse. Unified Buffer size is set in `config.py`. — [OpenTPU README](https://github.com/UCSBarchlab/OpenTPU)
- Precision: vectors and weights are always 8-bit integers in hardware (the functional simulator also has a 32-bit float mode). Adder width is capped at 32 bits, "creating the potential for uncaught overflow". Normalization is "programmable at synthesis-time, but not at run-time"; by default the upper 24 bits are dropped to produce an 8-bit result. — [OpenTPU README](https://github.com/UCSBarchlab/OpenTPU)
- Stated instruction latencies: `RHM`/`WHM` M cycles for M vectors; `RW` N*N/64 cycles for an NxN array plus up to 3 cycles through the FIFO; `MMC` L+2N cycles for L vectors on an NxN array; `ACT` L+1 cycles. — [OpenTPU README](https://github.com/UCSBarchlab/OpenTPU)
- No "repeat" flags and no dynamic scheduling: the assembler/compiler must statically schedule and pad with NOPs. — [OpenTPU README](https://github.com/UCSBarchlab/OpenTPU)

#### Limitations and performance
- README FAQ lists missing features as "Convolution, pooling, programmable normalization". Scope is "the inference phase" only; training is not mentioned. — [OpenTPU README](https://github.com/UCSBarchlab/OpenTPU)
- No clock, area, or power figures exist: "As of the alpha release, we do not have hard synthesis figures for the full 256x256 OpenTPU." No FPGA board is named in the README. — [OpenTPU README](https://github.com/UCSBarchlab/OpenTPU)
- Verilog path: "PyRTL can output structural Verilog for the design, using the `OutputToVerilog` function"; multiple users report failing to get usable or readable Verilog out of it (issues #5, #7, #9). — [OpenTPU README](https://github.com/UCSBarchlab/OpenTPU); [OpenTPU issues](https://github.com/UCSBarchlab/OpenTPU/issues)
- Reference point, Google's actual TPU v1: 65,536 8-bit MACs, 92 TOPS peak, 28 MiB software-managed on-chip memory, deployed since 2015, and a "deterministic execution model" chosen to meet 99th-percentile response-time requirements. — [Jouppi et al., ISCA 2017, arXiv:1704.04760](https://arxiv.org/abs/1704.04760)

#### Forks, ports and derivatives
- The only documented run on real FPGA hardware found: a Harvard Library Innovation Lab note (Jenevieve Haggard, 2026-06-16) hand-ported OpenTPU to SystemVerilog (systolic matrix unit, weight memory, instruction decoder, activation logic, host interface) on an Alchitry Pt v2 (Artix-7, about $300, USB 3.0 to host). Output matched a NumPy reference on a 200-vector benchmark. Reported speed: about 2x end-to-end and 4x compute-only versus the original Python simulator, slower than CPU BLAS on small inputs, with USB round-trip dominating. No clock rate, utilization or absolute latency is given; most code was written by AI coding agents. — [LIL blog, "An open hardware TPU on your desk"](https://lil.law.harvard.edu/blog/2026/06/16/an-open-hardware-tpu-on-your-desk/)
- `saurabhhgupta/OpenTPU` (last push 2018-03-23): "Add-on to the OpenTPU implementation with application to the PYNQ"; README says it adds "convolution, pooling, and programmable normalization". 1 star, no evidence of adoption. — [saurabhhgupta/OpenTPU](https://github.com/saurabhhgupta/OpenTPU)
- `csirlin/OpenTGPTPU` (most-starred fork: 14 stars, 293 commits, last push 2025-06-01): "Fork of github.com/UCSBarchlab/OpenTPU for the TGPTPU project", self-described "True general purpose tensor processing unit". Its future-work list includes a compiler, data movement between the Unified Buffer and weight FIFO, bitwidths other than 8-bit, and removing manually inserted NOPs. No FPGA target or paper is cited. — [csirlin/OpenTGPTPU](https://github.com/csirlin/OpenTGPTPU)
- All other forks checked (TPUNexus, renxuanle, JieQunLee, etc.) are unmodified snapshots with last push 2017-12-06. — [OpenTPU forks](https://github.com/UCSBarchlab/OpenTPU/forks)
- **Name collision to avoid:** `FeSens/openTPU` (created 2026-09-24, 1,002 stars, Apache-2.0, SystemVerilog, last push 2026-11-11) is an unrelated LLM-inference accelerator (Kintex-7 xc7k480t at 133.33 MHz, VU9P BCU1525 at 150 MHz; int8/4-bit weights held in card DDR3/DDR4 and streamed to a systolic matrix unit; e.g. 59 tok/s for LFM2.5-230M). Its README does not mention UCSB. Community ports to Tang Nano 20K, XCU200 and ZCU104 exist. It is inference-only and LLM-oriented, so outside this reader's scope, but its "weights in DRAM, one bitstream serves all models" design is the same overlay pattern. — [FeSens/openTPU](https://github.com/FeSens/openTPU)

### Inferences
- Architecturally, OpenTPU weights are runtime-swappable: `RW` pulls tiles from weight memory, each MAC double-buffers its weight, and `MMC.S` flips tiles without stopping. Nothing about the weights is baked into logic. What is missing is any way to *write* weight memory from the host or from an on-chip learner: the ISA has no instruction for it, and weight DRAM is a simulation stub initialised from a `.npy` file. Adding that path is an addition outside the existing core, not a redesign.
- Illustrative arithmetic from the README's cycle formulas (clock is my assumption, since no synthesis numbers exist): a single-vector dense layer costs about 1+2N cycles for `MMC` plus about 2 for `ACT`. For N=16 that is roughly 35 cycles, i.e. about 0.35 µs at 100 MHz; for N=256 about 515 cycles, i.e. about 5 µs, and reloading one 256x256 tile costs 1,024 cycles (about 10 µs). So an OpenTPU-style overlay is inherently in the sub-microsecond to tens-of-microseconds class per layer, not the nanosecond class of unrolled designs.
- With zero commits since 2017, unanswered issues, and a known bug report against the multiplier code, OpenTPU should be treated as a readable architectural reference (about 128 commits of PyRTL), not a dependency. The Harvard port suggests a clean-room SystemVerilog rewrite is tractable.
- There is no peer-reviewed OpenTPU paper; the README and the Google TPU paper are the only primary documentation.

### Gaps
- No published Fmax, LUT/DSP/BRAM counts or measured latency for OpenTPU on any FPGA; the Harvard note gives only relative speedups and I could not find its source repository.
- I did not find any fork or follow-up that adds training/backpropagation to OpenTPU.
- I could not verify from a fetched primary page the TPU v1 details commonly quoted beyond the abstract (700 MHz clock, 24 MiB Unified Buffer, 4 MiB accumulators, 8 GiB weight DRAM); only the abstract-level figures above were confirmed.
- Whether `OutputToVerilog` on current PyRTL 1.0.x produces a design that closes timing on an UltraScale+ part such as the U50's XCU50 is untested in any source found.

## Key Question 2: What other open or freely available FPGA ML toolflows exist as of late 2026, and are their weights fixed at synthesis or runtime-reloadable?

### Takeaway
The living, well-maintained open toolflows (hls4ml, FINN/FINN+ with Brevitas, the LUT-network family) are all dataflow designs that bake weights into the bitstream by default and deliver ns-to-µs latency; the open overlay designs whose weights live in memory (VTA, Tensil, NVDLA, DnnWeaver, OpenTPU) are all abandoned or archived, with Gemmini the only actively maintained one and Vitis AI no longer supporting the Alveo U50. Only FINN (runtime-writable weights in `internal_decoupled` mode), hls4ml (`BramFactor`, flagged for re-implementation) and SLAC's SNL offer a documented route to reloadable weights inside a dataflow design.

#### hls4ml
- Active: last push 2026-11-20, 2,211 stars, Apache-2.0, latest release v1.3.0 "iris" published 2026-03-20. — [fastmachinelearning/hls4ml](https://github.com/fastmachinelearning/hls4ml)
- Backends: Vitis HLS (2022.2+) is the main one; Vivado HLS is discontinued; oneAPI (Altera support dropped from oneAPI 2025.1) and Quartus/Intel HLS (discontinued); Siemens Catapult for ASIC and FPGA. — [hls4ml paper, arXiv:2512.01463 (Dec 2025)](https://arxiv.org/abs/2512.01463)
- Layers: Dense, 1D/2D convolution, LSTM/GRU, Einsum, batch/layer norm, multi-head attention (via HGQ2 front end, Vitis backend only); generic GNNs still in development. — [arXiv:2512.01463](https://arxiv.org/abs/2512.01463)
- Weight storage by strategy: **Latency** = fully unrolled constant-matrix-vector multiply with weights embedded in the multiplier circuits; **Resource** = weights stored in BRAM with MAC units time-shared per reuse factor; **Distributed Arithmetic (da4ml)** = shift-and-add adder graphs with no DSPs, generally not supporting reuse factor above one. — [arXiv:2512.01463](https://arxiv.org/abs/2512.01463)
- `io_parallel` is the default for minimum latency on small models; `io_stream` uses FIFOs for larger models. — [arXiv:2512.01463](https://arxiv.org/abs/2512.01463)
- Reported jet-tagging results on XCVU9P at a 5 ns clock: HGQ + DA strategy 75.9% accuracy, 3 clock cycles (12.1 ns), 0 DSP, 2,891 LUT, 651 FF, II=1; HGQ + Latency strategy 76.9%, 5 cycles (23.6 ns), 55 DSP, 13,303 LUT. MNIST on XCVU13P: 97.7%, 2 cycles (10 ns), 9,671 LUT. SVHN CNN: 93.9%, 1,045 cycles (5.2 µs), 53k LUT. — [arXiv:2512.01463](https://arxiv.org/abs/2512.01463)
- Deployed context: LHC level-1 triggers with roughly 10 µs latency budgets; other cited uses include a 44 ns malware detector at 100 Gbps and fusion plasma mode tracking at 7.7 µs. — [arXiv:2512.01463](https://arxiv.org/abs/2512.01463)
- Runtime weights: "hls4ml can optionally store weights in BRAMs external to the design" (Vivado/Vitis and Catapult backends). `BramFactor` is a model-level threshold; layers with more weights than it get their weight arrays exposed as `#pragma HLS INTERFACE bram` ports. The user is responsible for loading weights correctly, and the docs state "This feature is being evaluated for re-implementation." — [hls4ml docs: Loading weights from external BRAM](https://fastmachinelearning.org/hls4ml/advanced/bramfactor.html)
- The hls4ml 2025 overview paper does not describe on-chip training or weight updates anywhere in the text I could read. — [arXiv:2512.01463](https://arxiv.org/abs/2512.01463)
- da4ml (distributed-arithmetic compiler used by hls4ml): LGPL-3.0, last push 2026-04-15. — [calad0i/da4ml](https://github.com/calad0i/da4ml)

#### FINN, Brevitas, QONNX, FINN+
- FINN: last push 2026-11-20, 1,093 stars, BSD-3-Clause, but latest tagged release is still v0.10.1 from 2024-07-08. — [Xilinx/finn](https://github.com/Xilinx/finn)
- FINN+ describes upstream FINN as "an experimental framework from the Integrated Communications and AI Lab of AMD Research & Advanced Development". — [eki-project/finn-plus](https://github.com/eki-project/finn-plus)
- Brevitas (PyTorch quantization-aware training front end): last push 2026-11-20, release v0.13.4 on 2026-11-13, 1,601 stars. — [Xilinx/brevitas](https://github.com/Xilinx/brevitas)
- QONNX (shared interchange format for FINN and hls4ml): v1.0.0 released 2026-02-19, Apache-2.0. — [fastmachinelearning/qonnx](https://github.com/fastmachinelearning/qonnx)
- FINN+ is a fork by Paderborn University (Computer Engineering Group and PC2) that "incorporates all upstream FINN development" and adds transformer/attention support, automatic folding and FIFO sizing, "an enhanced build flow for Alveo cards", multi-FPGA inference and C++ drivers; release v1.6.2 on 2026-11-13. — [eki-project/finn-plus](https://github.com/eki-project/finn-plus)
- FINN memory modes for the matrix-vector unit (MVAU): **internal_embedded** ("Parameters are embedded directly into the hardware module as constants", via `params.h`); **internal_decoupled** (default; weights in `.dat` files held in a weight memory and streamed to the MVAU through a FIFO by `memstream.v`); **external** (weights supplied from outside the IP at runtime, "experimental" with limited support). HLS MVAU supports all three; RTL MVAU supports decoupled and external. — [FINN docs: Memory Modes](https://finn-dev.readthedocs.io/en/latest/reference/mem-modes.html)
- `internal_decoupled` "enables runtime weight updates through an AXI-Lite interface". `ram_style` selects `auto`, `block` (BRAM), `distributed` (LUTRAM) or `ultra` (URAM); URAM requires `runtime_writeable_weights=1` on non-Versal devices. — [FINN docs: Memory Modes](https://finn-dev.readthedocs.io/en/latest/reference/mem-modes.html)
- Stated trade-off: embedded mode has a smaller footprint but can cause very long HLS synthesis times; decoupled mode gives control over memory primitives and faster synthesis at a "slightly higher resource footprint" for the weight streamer and FIFO. — [FINN docs: Memory Modes](https://finn-dev.readthedocs.io/en/latest/reference/mem-modes.html)
- Maintainer explanation (fpjentzsch, 2024-06-10): `load_runtime_weights()` targets weights "stored in a FINN memstreamer IP with an AXI-lite interface inside the FPGA" and streamed to the MVAU; `load_external_weights()` targets weights "stored in DRAM and streamed into the FINN accelerator by a DMA core". For LUTRAM/BRAM, reloading is optional because contents are in the bitstream; for URAM they must be loaded. A March 2026 follow-up asking whether anyone had `external` mode working got no reply. — [FINN discussion #1099](https://github.com/Xilinx/finn/discussions/1099)
- Latency reference points: original FINN BNN on ZC706 reached 12.3 M classifications/s at 0.31 µs latency on MNIST and 21,906/s at 283 µs on CIFAR-10/SVHN, under 25 W. — [Umuroglu et al., FPGA 2017, arXiv:1612.07119](https://arxiv.org/abs/1612.07119)
- Joint hls4ml + FINN MLPerf Tiny submission (Pynq-Z2, Arty A7-100T): latency "as low as 20 µs" and energy "as low as 30 µJ per inference". — [Borras et al. 2022, arXiv:2206.11791](https://arxiv.org/abs/2206.11791)

#### Apache TVM VTA
- VTA is a "programmable accelerator" template with a two-level ISA (task-level ISA plus microcode-level ISA of single-cycle tensor-tensor operations), a JIT compiler runtime, and a parameterizable architecture, deployed on "edge-class FPGAs". — [Moreau et al., arXiv:1807.04188](https://arxiv.org/abs/1807.04188)
- TVM lead tqchen, 2024-11-14: "As one of the first step, we plan to phase out the legacy VTA flow"; it "will remain available in past releases" and is "not actively maintained as of now". — [TVM forum: Phasing out Legacy Components](https://discuss.tvm.apache.org/t/phasing-out-legacy-components/17703)
- `apache/tvm-vta`: last push 2024-04-10, 374 stars, not archived. — [apache/tvm-vta](https://github.com/apache/tvm-vta)

#### Tensil
- **Archived by owner on 2025-10-26** (read-only). Last code commit 2022-08-17. Tutorials cover PYNQ Z1, Ultra96-V2, Arty A7 and ZCU104; accepts ONNX and frozen TensorFlow graphs; headline figure is "ResNet at 300 FPS on ZCU104". — [tensil-ai/tensil](https://github.com/tensil-ai/tensil)

#### NVDLA
- `nvdla/hw`: last push 2022-03-02, 2,210 stars, 204 open issues, not archived. — [nvdla/hw](https://github.com/nvdla/hw)
- The official updates page lists releases only through 2018 (NVDLA v2 configurable release 2018-04-19) (snippet). — [nvdla.org updates](https://nvdla.org/updates.html)
- Architecture: convolution core with a convolution buffer for weights and features, SDP (activation/scaling), PDP (pooling), CDP (LRN), configured over a 32-bit CSB register bus, with a DBB AXI-like interface to system DRAM and an optional second interface to SRAM. Weights are trained offline and placed in memory by the host. Supports int8/int16/fp16 from the compiler. Framed as inference hardware. — [NVDLA Primer](https://nvdla.org/primer.html)

#### Gemmini
- Active: last push 2026-11-21, 1,590 stars; latest tagged release v0.7.1 from 2023-05-22. — [ucb-bar/gemmini](https://github.com/ucb-bar/gemmini)
- A Chisel generator in the Chipyard ecosystem; a RoCC accelerator driven by custom RISC-V instructions from a Rocket or BOOM core. Default 16x16 systolic array, 8-bit scratchpad inputs and 32-bit accumulators; output-stationary or weight-stationary dataflow selectable at runtime. Data (including weights) is moved from main memory into the scratchpad with `mvin`. Supports matmul, convolution (`gemmini_loop_conv_ws`), experimental max-pooling and I-BERT-style norm ops. FPGA use is via FireSim simulation; no specific boards are listed. — [Gemmini README](https://github.com/ucb-bar/gemmini)

#### LUT-based networks (LogicNets, PolyLUT, NeuraLUT, DWN and successors)
- A June 2025 survey traces the lineage LUTNet (2019), NullaNet (2019), LogicNets (FPL 2020), PolyLUT (ICFPT 2023), PolyLUT-Add, NeuraLUT (FPL 2024), AmigoLUT (2025), CompressedLUT/ReducedLUT (2024), DiffLogicNet (2022), DWN (2024) and TreeLUT (2025, gradient-boosted trees rather than a DNN). — [Guo, "A Survey on LUT-based Deep Neural Networks Implemented in FPGAs", arXiv:2506.07367](https://arxiv.org/abs/2506.07367)
- Survey comparison table (figures quoted from the original papers), jet substructure "JSC" low-accuracy tier: DWN-sm 74%, 110 LUTs, 1,094 MHz, 1.5 ns; NeuraLUT 72%, 4,684 LUTs, 3 ns; PolyLUT 72%, 12,436 LUTs, 5 ns; LogicNets 72%, 37,900 LUTs, 13 ns. — [arXiv:2506.07367](https://arxiv.org/html/2506.07367v1)
- Same table, MNIST: TreeLUT 96%, 3,499 LUTs, 2.3 ns; DWN-sm 97%, 692 LUTs, 2.4 ns; DWN-lg 98.3%, 4,082 LUTs, 6.0 ns; NeuraLUT 96%, 54,798 LUTs, 12 ns; PolyLUT 96%, 70,673 LUTs, 16 ns. Network intrusion (NID): TreeLUT 92%, 89 LUTs, 1.0 ns; LogicNets 91%, 15,900 LUTs, 11 ns. — [arXiv:2506.07367](https://arxiv.org/html/2506.07367v1)
- Stated limits: LUT cost grows exponentially with neuron fan-in; existing LUT-based DNNs are "mainly applied to small-scale networks"; TreeLUT models must be retrained from scratch when updated. — [arXiv:2506.07367](https://arxiv.org/html/2506.07367v1)
- DWN (Differentiable Weightless Neural Networks) claims, on JSC, slightly higher accuracy than NeuraLUT with 43.1x fewer LUTs and 1.57x lower latency (snippet). — [Bacellar et al., arXiv:2410.11112](https://arxiv.org/abs/2410.11112)

#### Notable newer entrants, 2024 to 2026
- **SNL (SLAC Neural Network Library)** with Auto-SNL (Aug 2025): "SNL's key feature is the ability to dynamically update model weights without requiring FPGA resynthesis." Weights and biases are loaded through AXI-Lite registers while AXI-Stream carries inference data. Benchmarked against hls4ml on ZCU102 at a 10 ns clock. — [Rahali et al., arXiv:2508.21739](https://arxiv.org/abs/2508.21739)
- **On-chip online learning with KANs** (MIT, Feb 2026, revised May 2026): forward pass, backward pass and in-place parameter update in one kernel on XCVU13P; one full update takes 50 ns, 70 ns and 140 ns post-route on three tasks, using e.g. 430 LUT / 199 FF / 4 DSP for the smallest and 10,592 LUT / 3,858 FF / 84 DSP for qubit readout, with no BRAM. Custom Python-to-Vitis-HLS generator, not hls4ml. — [Hoang, Gupta, Harris, arXiv:2602.02056](https://arxiv.org/abs/2602.02056)
- **ConvLUT** (Nov 2026): fully unrolled LUT-mappable convolutional architectures for MLPerf Tiny, inference latency below about 50 ns, and at least 20 percentage points higher CIFAR-10 accuracy than earlier MLP-style LUT models. — [Andronic et al., arXiv:2611.11507](https://arxiv.org/abs/2611.11507)
- **TsetlinWiSARD** (DAC 2026): on-chip FPGA training of weightless (RAM/LUT-node) networks with Tsetlin automata; claims 93.3% lower latency and 22% fewer resources than other FPGA training accelerators. — [Duan et al., arXiv:2603.24186](https://arxiv.org/abs/2603.24186)
- **Tensor-compressed transformer training on an Alveo U50** (2025): end-to-end single-batch training with all parameters and gradients on chip, under 6 MB BRAM and 22.5 MB URAM. — [Tian et al., arXiv:2501.06663](https://arxiv.org/abs/2501.06663)
- **AutoWS** (2023): partial streaming of weights from off-chip memory into layer-pipelined (dataflow) accelerators, built on fpgaConvNet. — [arXiv:2311.04764](https://arxiv.org/abs/2311.04764)
- Other flows named in hls4ml's comparison table: Intel FPGA AI Suite, MERA, HPIPE/H2PIPE, MASE, cgra4ml (noted as storing weights in off-chip memory), chisel4ml, tinyHLS, fpgaConvNet; DeepHLS, PipeCNN, DeepBurning and FP-DNN are described as not actively maintained. — [arXiv:2512.01463](https://arxiv.org/abs/2512.01463)
- fpgaConvNet model/optimiser repo: last push 2024-11-07, GPL-3.0. — [AlexMontgomerie/fpgaconvnet-model](https://github.com/AlexMontgomerie/fpgaconvnet-model)

## Key Question 3: What is the architectural trade-off between overlay/processor-style accelerators and fully unrolled dataflow designs, and what is lost when weights must be mutable?

### Takeaway
Dataflow designs get their ns-to-µs latency and II=1 throughput precisely by specialising logic to known weights (constant multipliers, shift-add graphs, per-weight bit widths, truth tables) and pay with a new bitstream per model; overlays keep weights as data in BRAM/URAM/DRAM/HBM and switch models with no rebuild, but add processor-like control, sequential layer execution and memory traffic that put them in the µs-to-ms class. Making weights mutable in a dataflow design costs the constant-folding gains (DSPs and LUTs come back) but not the pipeline structure, and published mutable-weight fabric designs still reach 50 to 140 ns per train step.

### Cited Findings
- Standard taxonomy: **streaming architectures** use "one distinct hardware block for each layer of the target CNN, where each block is optimised separately"; **single computation engines** use "a single computation engine, typically in the form of a systolic array of processing elements or a matrix multiplication unit, that executes the CNN layers sequentially" and "favours flexibility over customisation". — [Venieris, Kouris, Bouganis, "Toolflows for Mapping CNNs on FPGAs", arXiv:1803.05900](https://arxiv.org/abs/1803.05900)
- Streaming cost: "the increased efficiency comes with long compilation times since a new bitstream has to be generated for each CNN." Streaming tools such as FINN and Haddoc2 keep all weights on-chip, which caps network size. — [arXiv:1803.05900](https://arxiv.org/abs/1803.05900)
- Overlay benefit: "the same bitstream can target many CNNs without the overhead of bitstream-level reconfiguration." Overlay cost: "inefficiencies are introduced due to control mechanisms that resemble those of a processor" and "the one-size-fits-all approach can lead to high variability in the achieved performance". — [arXiv:1803.05900](https://arxiv.org/abs/1803.05900)
- Overlay latency drivers: single-engine designs rely on tiling and double buffering to hide off-chip transfer latency. — [arXiv:1803.05900](https://arxiv.org/abs/1803.05900)
- Dataflow, constant weights, measured: 12.1 ns (3 cycles at 5 ns, II=1, 2,891 LUT, 0 DSP) for a jet tagger with distributed arithmetic, versus 23.6 ns, 13,303 LUT and 55 DSP for the same task with conventional constant multipliers on XCVU9P. — [hls4ml paper, arXiv:2512.01463](https://arxiv.org/abs/2512.01463)
- Value of knowing weights at synthesis: heterogeneous per-weight quantization (HGQ) cut LUTs by 50 to 95%, DSPs by 50 to 100% and latency by up to 80% on unrolled models; DSP/BRAM-aware pruning cut DSPs 2.2x to 12.2x. — [arXiv:2512.01463](https://arxiv.org/abs/2512.01463)
- Pushing the clock: the same DA jet tagger reached 756 MHz on XCVU9P (21 cycles, 27.8 ns), and 176 MHz on an Artix-7 XC7A35T (46 cycles, 261 ns). — [arXiv:2512.01463](https://arxiv.org/abs/2512.01463)
- hls4ml's Resource strategy (weights in BRAM, time-shared MACs) is "typically higher latency" than Latency strategy at the same reuse factor. — [arXiv:2512.01463](https://arxiv.org/abs/2512.01463)
- LUT networks, weights absorbed into truth tables: 1.0 to 21 ns latency at 235 to 1,094 MHz, from 89 to 236,541 LUTs depending on method and task. — [arXiv:2506.07367](https://arxiv.org/html/2506.07367v1)
- Dataflow at larger scale: FINN BNNs at 0.31 µs (MNIST) and 283 µs (CIFAR-10); MLPerf Tiny dataflow designs as low as 20 µs; a binary-weight ResNet-50 dataflow design on Alveo U250 above 2,700 FPS at under 2 ms (snippet). — [arXiv:1612.07119](https://arxiv.org/abs/1612.07119); [arXiv:2206.11791](https://arxiv.org/abs/2206.11791); [arXiv:2011.07317](https://arxiv.org/abs/2011.07317)
- Overlay / layer-sequential, measured: ResNet18 13.7 ms and YOLOv5n 13.7 ms (Vitis AI) on ZCU102; ResNet50 6.0 ms on Alveo U50. On the same U50, a weight-streaming dataflow design ran ResNet50 in 3.4 ms. — [AutoWS, arXiv:2311.04764](https://arxiv.org/abs/2311.04764)
- Moving weights off-chip in a dataflow design can backfire when bandwidth is short: ResNet50 on ZCU102 took 578.7 ms with weight streaming versus 21.1 ms layer-sequential. — [arXiv:2311.04764](https://arxiv.org/abs/2311.04764)
- Overlay instruction costs (OpenTPU model): `MMC` takes L+2N cycles and a tile reload N*N/64 cycles on an NxN array. — [OpenTPU README](https://github.com/UCSBarchlab/OpenTPU)
- Mutable weights in a dataflow design, cost in FINN: decoupled (RAM-backed, runtime-writable) weights carry a "slightly higher resource footprint" for the streamer and FIFO compared with embedded constants. — [FINN docs: Memory Modes](https://finn-dev.readthedocs.io/en/latest/reference/mem-modes.html)
- Mutable weights in a dataflow design, cost in SNL vs hls4ml (ZCU102, 10 ns clock, synthesis results): SNL consistently used more BRAM and mostly more FFs, and more LUTs on CNNs, while achieving lower latency than hls4ml on three of four models (hls4ml slightly ahead on the jet model). The paper does not isolate how much of the difference is due to reloadability. — [arXiv:2508.21739](https://arxiv.org/abs/2508.21739)
- Mutable *and* trained in fabric: full forward + backward + update in 50 to 140 ns at a 3.04 to 3.88 ns achieved clock on XCVU13P, parameters in LUTRAM/FF with arrays partitioned for parallel access and no external DRAM. The authors report that fixed-point MLP backprop "often diverge[s] or need[s] higher bitwidths" and scales roughly linearly in cost with parameter count, whereas KAN updates touch only the active spline coefficients. — [arXiv:2602.02056](https://arxiv.org/abs/2602.02056)
- Later work summarised in search results characterises overlays as scaling well but with "higher resource utilization and less performance compared to custom dataflow accelerators" and as better suited to "highly frequent model switching" (snippet; source papers' titles not verified). — [arXiv:2605.23630](https://arxiv.org/abs/2605.23630); [arXiv:2604.07523](https://arxiv.org/abs/2604.07523)

### Inferences
- Rough latency ladder for small models, combining the cited numbers: LUT networks 1 to 20 ns; unrolled constant-weight hls4ml MLPs 10 to 30 ns; unrolled designs with mutable register/LUTRAM weights 50 to 150 ns including a training step; folded or streamed dataflow (FINN, `io_stream`) 0.3 µs to hundreds of µs; small systolic overlay 0.3 to 10s of µs per layer; DPU-class overlays with off-chip weights 3 to 15 ms.
- What a dataflow design loses when weights become mutable: (1) constant-coefficient multipliers and distributed-arithmetic adder graphs, so generic multipliers return (DSP48s or LUT multipliers sized for the worst-case bit width); (2) unstructured pruning and per-weight bit widths, since a zero or narrow weight can no longer delete logic; (3) LUT absorption of weights plus activation into truth tables. The 2,891-LUT/0-DSP versus 13,303-LUT/55-DSP jet-tagger pair is a fair indicator of the order of magnitude of what constant folding buys, though it compares two constant-weight strategies rather than constant versus mutable.
- What it keeps: full pipelining, II=1, no instruction decode, and deterministic latency. This is why SNL remains latency-competitive with hls4ml and why the KAN learner reaches sub-150 ns.
- What an overlay loses: latency (2N-cycle systolic skew, sequential layers, weight-tile loads), and throughput per LUT. What it keeps for free: arbitrary weight changes, model-shape changes without a rebuild, and weight capacity limited by BRAM/URAM/HBM rather than LUT count.
- Weight placement sets both update cost and inference latency: registers/LUTRAM give fully parallel read access (needed for unrolled designs) but are costly per bit and are written serially over AXI-Lite unless a learner is on-chip; BRAM/URAM are dense but offer one or two ports, forcing folding (time-multiplexing) and hence µs latency; DRAM/HBM forces streaming and ms-class behaviour unless bandwidth is ample.
- For small models the U50's 8 GB HBM is irrelevant to latency; the relevant resources are LUTRAM/FF for parallel weights and URAM/BRAM for folded ones.

### Gaps
- No single source benchmarks the same small model on an overlay and on an unrolled dataflow design on the same FPGA; the ladder above stitches together different papers, devices and models.
- No source isolates the pure cost of "constant weights to register weights" for one fixed architecture (SNL vs hls4ml differ in more than weight storage).
- The hls4ml-vs-Versal-AI-Engine and "up to 2x worse than hand-written Verilog" statements in the hls4ml paper were read only in summary form.
- I found no measured Fmax or latency for a small systolic overlay (OpenTPU-like, N of 8 to 32) on UltraScale+.

## Key Question 4: Which of these is the most practical base for continuously or periodically updated weights, and is there published work making hls4ml/FINN-style dataflow designs runtime-reweightable?

### Takeaway
Yes, published and documented mechanisms exist: FINN's `internal_decoupled` memory mode with runtime-writable weights over AXI-Lite (maintained, in-tree), hls4ml's `BramFactor` external-BRAM weights (exists but flagged for re-implementation), SLAC's SNL (purpose-built for reloadable weights via AXI-Lite registers), and a 2026 MIT design that trains in fabric at 50 to 140 ns per update. For periodic host-driven updates FINN/FINN+ is the most practical maintained base; for continuous on-chip learning at the lowest latency, a custom HLS/RTL dataflow design with register or LUTRAM weights is what the literature supports, with OpenTPU useful as a reference for the memory-resident-weight overlay pattern but not as a code base.

### Cited Findings
- FINN: `internal_decoupled` is the default MVAU memory mode, holds weights in LUTRAM/BRAM/URAM, and "enables runtime weight updates through an AXI-Lite interface"; `runtime_writeable_weights=1` is mandatory for URAM on non-Versal devices such as the U50's UltraScale+ part. — [FINN docs: Memory Modes](https://finn-dev.readthedocs.io/en/latest/reference/mem-modes.html)
- FINN driver API: `load_runtime_weights()` writes weights held in the in-fabric memstreamer over AXI-Lite; `load_external_weights()` handles weights kept in DRAM and streamed by a DMA core. The `external` mode is documented as experimental, and a March 2026 user question about getting it working is unanswered. — [FINN discussion #1099](https://github.com/Xilinx/finn/discussions/1099); [FINN docs: Memory Modes](https://finn-dev.readthedocs.io/en/latest/reference/mem-modes.html)
- FINN+ adds an "enhanced build flow for Alveo cards" and is actively released (v1.6.2, 2026-11-13). — [eki-project/finn-plus](https://github.com/eki-project/finn-plus)
- hls4ml: `BramFactor` exposes large layers' weight arrays as BRAM interface ports so "a user can use this interface to implement a weight-reloading scheme"; model-level only; "being evaluated for re-implementation". — [hls4ml docs: external BRAM weights](https://fastmachinelearning.org/hls4ml/advanced/bramfactor.html)
- hls4ml third-party work: a DOE SBIR Phase II project (Crossfield Technology with Fermilab) built a framework that "remotely updates weights and biases" in an hls4ml IP core on an Arria 10 SoC, described as portable to other Intel and Xilinx SoC FPGAs (snippet; workshop abstract only). — [CERN Indico contribution 5062809](https://indico.cern.ch/event/1156222/contributions/5062809)
- SNL: runtime weight and bias updates without resynthesis via AXI-Lite registers; latency competitive with or better than hls4ml on three of four benchmark models at a 10 ns clock on ZCU102; costs more BRAM and FFs; tunable only in input and weight precision; results are synthesis-only with no on-hardware measurements; two configurations failed (KWS at <32,16> exceeded DSP/LUT capacity). — [arXiv:2508.21739](https://arxiv.org/abs/2508.21739)
- On-chip continuous learning in fabric: single-sample online SGD with forward, backward and in-place update in one kernel; 50/70/140 ns per update; parameters fully on-chip; built with a custom generator emitting Vitis HLS C++ (`ap_fixed` with rounding and saturation), implemented with Vivado 2024.1. Limitations: batch-size-one SGD only, no Adam, post-route results only for the KAN designs, no repository link in the text. — [arXiv:2602.02056](https://arxiv.org/abs/2602.02056)
- On-chip training is feasible on the U50 itself: a tensor-compressed transformer trainer fits in under 6 MB BRAM plus 22.5 MB URAM on an Alveo U50 with all parameters and gradients on chip. — [arXiv:2501.06663](https://arxiv.org/abs/2501.06663)
- Weightless/LUT-node networks can be trained on-chip: TsetlinWiSARD (DAC 2026) presents an FPGA training architecture for WNNs. — [arXiv:2603.24186](https://arxiv.org/abs/2603.24186)
- Hybrid weight placement for larger dataflow designs: AutoWS splits each layer's weights into static on-chip fragments and dynamic fragments reloaded from off-chip memory through a shared buffer. — [arXiv:2311.04764](https://arxiv.org/abs/2311.04764)
- OpenTPU as a base: weights are memory-resident and double-buffered per MAC, but the project has had no commits since 2017-12-06, has no synthesis results, no convolution, and inference only. — [OpenTPU README](https://github.com/UCSBarchlab/OpenTPU); [GitHub API](https://api.github.com/repos/UCSBarchlab/OpenTPU)
- Maintained overlay alternative: Gemmini (active, weights via `mvin` from main memory, runtime-selectable dataflow) but tied to a RISC-V Rocket/BOOM host and FireSim. — [Gemmini README](https://github.com/ucb-bar/gemmini)

### Inferences
- Ranking for this reader's goal (U50, small models, lowest latency, mutable weights), my judgement from the evidence above:
  1. **Custom unrolled dataflow with weights in registers/LUTRAM and an on-chip or AXI-Lite update path**, following the SNL and Hoang et al. pattern. Best latency (tens to low hundreds of ns), supports true online learning, but nothing reusable is confirmed open source.
  2. **FINN/FINN+ with `internal_decoupled` + `runtime_writeable_weights`.** The only maintained, documented, in-tree feature; has an Alveo flow. Suited to periodic updates pushed by the host, not per-sample learning, because writes go word-by-word over AXI-Lite into a memstreamer and the MVAU is folded around a RAM.
  3. **hls4ml Resource strategy + `BramFactor`.** Workable but officially unstable; hls4ml's best latency results (Latency/DA strategies) are exactly the ones that cannot have mutable weights.
  4. **OpenTPU-style overlay (clean-room rewrite).** Simplest mental model for mutable weights and model-shape changes; µs-class latency; needs everything built (memory controllers, PCIe/XDMA or QDMA host path, timing closure).
  5. Gemmini, VTA, Tensil, NVDLA, Vitis AI DPU: either too heavy (SoC-bound), abandoned, closed, or not supported on the U50.
- A caveat for FINN runtime weights that the docs do not spell out: FINN's streamlining typically folds scale factors and batch-norm into integer weights and multi-threshold activations, so new weights must be produced by the same quantization pipeline and fit the same bit widths and thresholds. An on-chip learner would have to update in that integer domain. I did not find a FINN source confirming or denying this, so treat it as a design risk to check.
- A hybrid is plausible and consistent with the literature: unrolled datapath with generic (non-constant) multipliers, weights in FF/LUTRAM for parallel read, a shadow copy for atomic swap in the manner of OpenTPU's two weight buffers per MAC, and an update engine fed either by the host over PCIe or by an on-chip gradient kernel.
- If learning must be continuous and on-chip, the KAN result suggests choosing a model family whose update is sparse/local (spline coefficients, table entries, weightless RAM nodes) instead of dense MLP backprop, because dense fixed-point backprop is both costlier and less numerically stable in the cited experiments.
- LUT-network methods are the wrong base for adaptivity as published; any runtime change means retraining and re-running synthesis and place-and-route. On-chip-trainable weightless networks (TsetlinWiSARD) are the nearest LUT-flavoured alternative.

### Gaps
- No published design was found that combines an OpenTPU/TPU-style systolic overlay with on-chip training on an FPGA.
- No measurement was found of FINN runtime-weight update time (e.g. ms to rewrite a layer over AXI-Lite) or of whether inference must be paused during the write.
- I found no open-source repository for SNL/Auto-SNL or for the KAN online-learning generator, so "base" here means architectural precedent, not reusable code, until those are located.
- No source addresses partial reconfiguration (DFX) or CFGLUT5-style reconfigurable LUTs as a weight-update mechanism for LUT networks; this was not searched in depth.
- The Crossfield/Fermilab hls4ml weight-update framework is known only from a workshop abstract; availability and design details are unverified.
- No source quantifies the latency of PCIe (XDMA/QDMA) host round-trips on the U50 for small-model inference, which the Harvard note suggests can dominate end-to-end time when the host is in the loop.
